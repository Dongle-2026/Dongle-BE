# 돈글돈글 완성본 제출 계획 — 남은 격주 2회

작성 기준: 2026-09-29. 이 문서는 기존 3회 개발 계획보다 우선하는 최신 일정이다.

진행 업데이트: 오류 코드·요청 ID·단계별 지연 관측 구현 및 테스트 완료([상세](AI_OBSERVABILITY.md)). 짧은 실모델 진단에서 요약 47.1초, 임베딩 1.1초를 확인했다. 전체 AI 안정화·비동기 작업 큐·앱 통합은 아직 남아 있다.

## 1. 일정과 완료의 의미

사용자 요구: 남은 2회차 안에 개발을 마치고 완성본 제출, 그동안 격주보고서 2회 작성, 최종발표 준비.
여기서는 **앞으로 남은 격주 기간 2개**를 A·B로 부른다. 기존 보고서의 ‘2차’ 번호와 혼동하지 않는다. 학교의 확정 제출일은 아직 받지 않았으므로 아래 날짜는 계획용이다. 만약 ‘전체 보고서 제2회 제출일까지 완료’라는 의미라면 이 일정보다 짧으므로 날짜와 범위를 즉시 재조정해야 한다.

| 기간 | 개발 목표 | 제출·증빙 |
|---|---|---|
| A: 9/29~10/12 (가정) | 주요 API와 앱 연결, AI 오류 원인 확인·안정화, 핵심 기능 전체를 한 번에 시연 | 보고서 1: 문제·선택 이유·개인 역할·실제 결과, 화면/로그 별지 |
| B: 10/13~10/26 (가정) | 초반에 기능 개발 종료, 후반은 통합 테스트·빌드·결함 수정만 수행 | 보고서 2: 완성본 검증, 최종 실행본·소스·설명서 |
| 최종발표: 학교 일정에 맞춤 | 신규 기능 개발 없이 시연 연습·발표자료 마무리 | 발표자료, 시연 영상, 백업 실행 환경 |

‘완료’는 API 파일이 존재한다는 뜻이 아니다. React Native 앱에서 실제 API를 호출하고 DB에 저장된 결과를 다시 읽으며, 오류 처리와 재실행 방법까지 검증되어야 한다. 현재는 백엔드 기반 구현 단계이며 완성본은 아니다.

최근 검증: 백엔드 54건 통과(실모델 1건 생략), Node 8건 통과. 별도로 실행한 최신 실모델 1건은 실패했다. 전체 AI 경로가 안정적이라고 보고서에 쓰면 안 된다.

## 3. 완성본 범위와 우선순위

### 반드시 완성할 핵심 사용자 흐름

1. 로그인 → 관심 분야/프로필 설정 → 앱 재실행 후 인증 상태 확인.
2. 뉴스 목록·검색 → 기사/카드 상세 → 원문·용어 설명 → 읽음 기록.
3. 뉴스 저장 → 저장 목록 → 저장 해제 후 목록 반영.
4. 개인화 추천 → 추천 이유 표시 → 읽음 행동 이후 변화 확인.
5. 소비 등록·수정·삭제 → 월별 집계·예산·추세 → 실제 집계 기반 인사이트.
6. 관리자 기사 AI 처리 → 검증된 결과 저장 → 앱에서 조회. 생성 실패 시 이전 결과 유지.
7. 네트워크 오류·만료 토큰·빈 결과·생성 미완료 상태에서 앱이 멈추지 않음.

정책 조회·조건 기반 추천·북마크·앱 내 알림도 기존 구현을 앱에서 검증한다. 제안서에 들어간 기능은 검증 없이 완료 처리하지 않는다.

### 조건부 기능: A 초반에 팀 결정 필요

- 모바일 소셜 로그인: 제공자 콘솔 및 앱 scheme 설정 필요. 제공하기로 했다면 B로 미루지 않고 A에서 실기기 검증한다. 미완료일 경우 로컬 로그인만으로 제출해도 되는지 지도교수/팀 합의가 필요하다.
- FCM 푸시: Firebase 프로젝트, 플랫폼 앱 등록, 권한 요청, 토큰 갱신/로그아웃 해제, 실제 수신 검증까지 해야 완료다. 계정 준비가 늦으면 앱 내 알림만 제공하는 범위 변경을 명시적으로 합의한다.
- 주가: 실제 데이터 공급원·키·이용 조건·실패 응답 확인이 필요하다. 기존 화면/API가 있더라도 최신 실제 시세 검증 전에는 완성으로 표시하지 않는다.
- 새 챗봇, 금융상품 추천, 추가 모델 학습은 현재 필수 범위에 새로 넣지 않는다. 기존 제출 제안서가 필수로 요구한다면 누락으로 기록하고 팀과 범위를 확정한다.

## 4. 바로 해야 할 개발 — 순서와 완료 기준

| 순서 | 작업 | 필요한 이유/방법 | 완료 기준 |
|---|---|---|---|
| 1 | AI 503 원인 관측 | Spring에 내부 오류 코드·소요시간 기록. 본문·개인정보·토큰은 로그 제외. timeout/모델 오류/출력 검증 실패를 구분 | 같은 입력으로 실패 원인을 식별, 차가운 시작/준비된 모델 각각 측정 |
| 2 | 생성 작업 상태 관리 | 현재 동기 생성은 모바일 요청에 너무 느림. DB 작업 테이블과 상태 조회, 중복 방지, 제한 재시도·재시작 복구 구현 | 요청은 작업 ID를 빠르게 반환, 성공/실패/진행 중 조회, 재시작 후 복구 시험 |
| 3 | 앱 API 연결 | 화면의 Mock Data를 실제 응답으로 교체. 공통 클라이언트에 토큰·오류·페이지네이션 처리 | 핵심 흐름을 iOS/Android에서 실제 DB로 시연 |
| 4 | 인증·사용자 데이터 보호 | 모바일 로그인 콜백, 토큰 만료/재발급, 타인 데이터 접근 차단, 기기 토큰 정리 | 만료/로그아웃/계정전환 및 타인 데이터 접근 테스트 |
| 5 | 배포·DB 재현성 | SQL 파일만으로 자동 적용되지 않음. 기존 DB 백업 후 스키마 적용, 설정·서비스 기동 순서 고정 | 다른 팀원 장비에서 문서만 보고 설치·실행, 데이터 보존 확인 |
| 6 | 품질·성능·오류 검증 | 한 번의 성공이 품질을 보장하지 않음. 고정 평가 기사 20건, 숫자/사실/근거·용어 위치 평가 | 성공/실패율, 지연 p50/p95, 오류 사례와 수정 결과 기록. 목표는 팀이 사전 확정 |
| 7 | 최종 빌드·시연 | Expo Go 동작과 독립 실행 앱은 다름. Dev Client 충돌 해결과 제출 형식 확인 | 학교 요구에 맞는 설치 파일/실행 방식, 실기기 재설치·시연 영상 확보 |

개발 중 생성한 결과를 미리 저장해 앱에서는 조회하는 구조를 기본으로 한다. 사전 생성은 정상 서비스 흐름이지만, 영상/발표에서 실시간 생성이라고 표현하면 안 된다. 시연용 결과 역시 실제 모델 결과와 스텁을 구분한다.

## 6. 보고서 2회 작성 방법

각 보고서는 연구 내용, 문제점 및 해결, 진도상황 확인, 기타 애로사항, 별지 순서로 작성한다. 기존 요구의 5페이지 이상은 제출 양식으로 편집한 뒤 실제 페이지 수를 확인한다. Markdown 길이로 페이지 수를 단정하지 않는다.

### 보고서 1 — 구현·연동 중심

- 연구 내용: 사용자 제공 프론트 진도는 ‘기존 UI 구현 현황’에 배치하고, 실제 API 연결 이후 변경점을 별도로 기록한다. 검색·소비 집계·AI 저장·추천 구현은 문제→선택 이유→본인 수정 파일/역할→검증 결과 순서로 설명한다.
- 문제점/해결: 기간 필터와 최신 이벤트 순서 오류, ltree 타입 오류, 실제 카드 스텁 덮어쓰기 위험을 코드와 테스트로 설명한다. AI 503은 해결 전까지 진행 중으로 남긴다.
- 진도: 기존 3회 계획을 남은 2회 완료 계획으로 압축한 근거와 기능 동결일을 기록한다.
- 애로사항: 앱 빌드 충돌, 모델 지연, 외부 계정 준비·실기기 접근 문제.
- 별지: API 요청/응답, 앱 연결 화면, 테스트 로그, 모델/프롬프트 버전, 개인별 실제 수행 표.

### 보고서 2 — 완성·평가 중심

- 연구 내용: 통합 흐름, 최종 빌드, 생성 작업 복구, 개인정보 보호, 평가 수행 내용을 실제 결과로 작성한다.
- 문제점/해결: 보고서 1의 미해결 항목이 어떻게 달라졌는지 같은 테스트 조건으로 비교한다.
- 진도: 기능별 완료 여부·증빙 링크·제외 합의·남은 한계를 제출 시점 기준으로 확정한다.
- 애로사항: 배포 비용/장비 성능/모델 사실성 한계와 운영 대책.
- 별지: 20건 평가표, 응답시간 표, iOS/Android 시나리오 결과, 최종 버전/설치 안내, 시연 화면.

작성 예: ‘AI 연동 완료’ 대신 ‘Spring→Node→Ollama→PostgreSQL 경로를 구현했다. 이전 실모델 성공 이력이 있지만 9/29 재검증은 약 120초 후 503으로 실패했다. 오류 관측과 비동기 처리를 보완하고 동일 입력으로 재검증할 예정이다.’

## 7. 최종발표와 제출 묶음

발표 순서: 청년 금융정보 이해의 어려움 → 핵심 사용자 흐름 → 실제 시연 → 구조/기술 선택 → 어려웠던 문제와 해결 → 정량 검증 → 개인 기여·한계.

- [ ] 시연: 로그인→뉴스 검색→카드/용어→저장→소비 인사이트. 발표 시간에 맞춰 핵심만 선정.
- [ ] AI 필요성: 요약·쉬운 설명·제안 문장은 모델, 금액 계산·인증·정책 조건 판정은 결정적 코드로 분리한 이유 설명.
- [ ] 기술 선택: React Native/TypeScript의 모바일 공통 UI, Spring의 인증·트랜잭션, Node의 모델 호출 분리, Ollama 로컬 실행, pgvector 유사도 계산.
- [ ] 근거: 실제 실패 사례와 개선 전후 수치. 측정하지 않은 정확도/절감률은 사용 금지.
- [ ] 백업: 시연 영상, 사전 생성 데이터, 설치 파일, 서버 실행 안내. 라이브와 녹화를 명확히 구분.
- [ ] 팀 기여: 담당 예정이 아니라 커밋·문서·테스트 증빙으로 실제 기여를 기록.
